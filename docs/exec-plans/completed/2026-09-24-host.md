## Purpose / Big Picture

WinShape Day Camp · Atlanta runs at a partner church, Grace Community Church. The church's coordinator (a "host") needs three things from WinShape: to see how their week is filling up, to register their volunteers for background-check vetting without emailing a spreadsheet to WinShape staff, and to pay WinShape's invoice for hosting the camp. Before this change a host who signed in landed in the staff console, where every page refused them. After it, Grace Patel (the seeded host coordinator, WorkOS role `host`) signs in and lands in a host portal of her own at `/host`, which shows only Grace Community Church's data:

- H1, host home: registrations for the Day Camp week against capacity and against last year, volunteers by vetting status, the invoice balance, and upcoming deadlines worked out from real rows.
- H2, volunteers: the volunteer list, "Download template", "Upload CSV" with a validation preview (the demo file has 40 rows: 37 valid and 3 with row-level reasons), fix a row inline or skip it, then "Submit 37 valid to vetting". Rows with unresolved errors are held back and stay visible. Nothing is dropped silently. A single volunteer can also be added by hand.
- H3, invoices: the church's invoices with period, amount and status, an invoice detail with line items, and Pay through the Fiserv sandbox (card `4242 4242 4242 4242` approves, `4000 0000 0000 0002` declines). The payment is recorded on the server and the invoice turns Paid.

To see it working, start the API and Vite (Concrete Steps), sign in as `grace.patel@winshape.example`, and walk Home, Volunteers (upload `e2e/fixtures/grace-volunteers.csv`), and Invoices.

## Decision Log

- Decision: A host user is linked to a church by a slice entity `HostMember` (email → `HostOrganization`). Every host endpoint resolves the organization from the signed-in staff email through that table and never takes an organization id from the request. A host-role user with no membership (or an admin) gets 403 with a plain message.
  Rationale: the parent plan says Grace sees only Grace Community Church's event. The email comes from the session cookie, which only WorkOS can set.
  Date/Author: 2026-09-24 / Claude
- Decision: The host event is a slice entity `HostEvent` pointing at the Day Camp · Atlanta "June week" session (June 12–16, 2028), with last year's registration count (88) and the vetting deadline (May 15, 2028) stored on it. Registrations this year are counted live from `Registrations` in that session.
  Rationale: last year has no session in the seed, and the Wave 1 lesson forbids adding sessions to Day Camp, which other specs register into. Storing the prior-year figure is what an import from the old system would do.
  Date/Author: 2026-09-24 / Claude
- Decision: The host portal is its own shell at `/host` (the shadcn Sidebar block, slimmer: Home, Volunteers, Invoices), mounted as a top-level route. This needs three small shared edits the slice section allows: `web/src/router.ts` (pick up `hostRoutes` from slice route files and guard `meta.auth: 'host'`; send a host who opens `/admin` to `/host`), `web/src/lib/nav.ts` (add `'host'` to `RouteMeta.auth`), and `api/Camp.Api/Auth/AuthEndpoints.cs` (a host signing in with no return path lands on `/host`).
  Rationale: a slice `routes` array can only add children of the guest layout or the staff console, and neither is the host shell. Spreading a third array is the smallest change that keeps the slice seam.
  Date/Author: 2026-09-24 / Claude
- Decision: No "Reports" nav entry. H1 is "Host home + reports"; the registrations comparison lives on it, and deeper reports are FR-96 (Bucket C).
  Rationale: a nav item pointing at the page you are on is a dead end.
  Date/Author: 2026-09-24 / Claude
- Decision: Vetting statuses are Not started, In progress and Approved. A volunteer sent to vetting starts at Not started (the volunteer has the background-check email but hasn't begun it). Seeded volunteers use all three.
  Rationale: the concept uses these three words; the spec's status vocabulary has no vetting set.
  Date/Author: 2026-09-24 / Claude
- Decision: An upload is stored with every row (`VolunteerUpload`, `VolunteerUploadRow`), each Valid, Error, Skipped, or Submitted. Every upload change (new upload, fix, skip, restore, submit) runs in a transaction that first takes an `UPDLOCK, HOLDLOCK` on the church's `HostOrganizations` row, so changes for one church are serialized; Submit revalidates under that lock and creates volunteers for exactly the rows it marks Submitted; Error rows stay held back and remain fixable. A new upload is refused while an earlier one still has rows that are Valid or Error, so no row can be hidden by a later file.
  Rationale: "an upload that silently drops bad rows" is the H2 trap. Persisting rows makes the preview survive a reload.
  Date/Author: 2026-09-24 / Claude
- Decision: Invoice status words are "Balance due" and "Paid" (the Part 2 payment vocabulary), not the concept's "Due". Payment follows the family balance payment's shape: insert a Pending row (one per invoice, unique filtered index), charge the gateway with the payment's idempotency key, then claim the Pending row with a conditional update to record the result. The amount is always the invoice's remaining balance, computed on the server.
  Rationale: the processor and SQL can't share a transaction; this makes double-clicks and retries safe.
  Date/Author: 2026-09-24 / Claude

Payment follows the family balance pattern: one Pending payment per invoice, with the amount set on the server and an idempotent key. Tests cover it: a decline leaves the balance due; replaying a key doesn't charge twice; six concurrent pays charge once.

Known gaps:
- Vetting status only moves from outside the portal. Nothing here advances Not started to In progress or Approved. The outbox event is the hand-off.
- "Download PDF" from the concept is not built.
- The invoice list has no search, because hosts have few invoices.
- The volunteer table has no row actions (the concept's "⋮" menu) or bulk selection.
- `Policies.Host` also admits admins, but the web guard sends admins to `/admin` because they have no church.

## Context and Orientation

The repository is a WinShape camp registration prototype: an ASP.NET Core minimal API in `api/Camp.Api` (EF Core, SQL Server), a Vue 3 + shadcn-vue app in `web/`, and Playwright specs in `e2e/`. `AGENTS.md` explains the slice seams: an `IEndpointModule` in `api/Camp.Api/Features/<Slice>/` is found by assembly scan; `IEntityTypeConfiguration<T>` classes are picked up by `ApplyConfigurationsFromAssembly`; an `ISeedModule` adds demo rows after the core seed (`api/Camp.Api/Data/Seed.cs`); web pages come from `web/src/features/<slice>/routes.ts`.

Auth: guests and staff sign in through WorkOS AuthKit (locally an emulator on port 4100). Staff carry a `camp:staff_role` claim (`cet`, `finance`, `host`, `admin`); `Policies.Host` in `api/Camp.Api/Auth/Identity.cs` accepts `host` and `admin`. `StaffUser` is the injected identity for staff endpoints (name, email, role). `IAuditLog.Record` stages an audit row before `SaveChanges`.

Money is integer cents throughout. The fake Fiserv gateway (`api/Camp.Api/Integrations/PaymentGateway.cs`) tokenizes a card number at `POST /api/fiserv-sandbox/tokenize` and charges a token; a number ending 0002 declines.

The Day Camp · Atlanta program (`day-camp-atlanta`) has `HostOrganization = "Grace Community Church"` and two sessions: "June week" (June 12–16, 2028, six grade pools of 20 = 120) from the core seed and "June week 2" from the staff-cx seed. This slice reads the first one and never adds sessions or registrations to it.

## Plan of Work

Milestone 1 builds the API. Entities: `HostOrganization` (name, city), `HostMember` (email unique, title, organization), `HostEvent` (organization, session, last-year registrations, vetting deadline), `HostVolunteer` (organization, names, email unique per organization, phone, date of birth, role, vetting status, created time, optional upload row), `VolunteerUpload` (organization, file name, uploaded by, time) with `VolunteerUploadRow` (row number, raw fields, status, issue, detail), `HostInvoice` (organization, optional event, number, description, period label, issued and due dates) with `HostInvoiceLine` and `HostInvoicePayment`. Endpoints live under `/api/host`, all with `Policies.Host`:

    GET  /api/host/me                                   organization, member title, event
    GET  /api/host/overview                             H1 numbers and deadlines
    GET  /api/host/volunteers                           list + counts by status
    POST /api/host/volunteers                           add one volunteer (same validation)
    GET  /api/host/volunteers/template.csv              the CSV template
    GET  /api/host/uploads/latest                       the latest upload, or 204
    POST /api/host/uploads                              { fileName, content } → preview
    PUT  /api/host/uploads/{id}/rows/{rowId}            fix a row, revalidated
    POST /api/host/uploads/{id}/rows/{rowId}/skip       skip it (kept, marked Skipped)
    POST /api/host/uploads/{id}/rows/{rowId}/restore    undo a skip
    POST /api/host/uploads/{id}/submit                  Valid rows → volunteers (Not started)
    GET  /api/host/invoices                             list
    GET  /api/host/invoices/{id}                        detail with lines and payments
    POST /api/host/invoices/{id}/pay                    { idempotencyKey, cardToken }

Validation rules for a volunteer row: first and last name required; email required, well formed, not repeated earlier in the file ("Same email as row N") and not already in the church's volunteer list ("Duplicate email"); date of birth required, a real date as MM/DD/YYYY or YYYY-MM-DD, and 18 or older on the event's first day; role one of Group leader, Check-in, Kitchen, Games, Crafts, First aid (blank means Group leader). Staff mutations (upload, fix, skip, restore, submit, add, pay) are audited; submit writes one `VolunteerVettingRequested` outbox event per volunteer, and a paid invoice writes a `HostInvoicePaid` receipt event.

Milestone 2 builds the web side: the host shell and the three pages, plus the router, nav type and sign-in landing edits named in the Decision Log.

Milestone 3 adds `e2e/host.spec.ts`: Grace signs in and lands on H1, uploads the demo CSV and sees 40 rows, 37 valid and 3 errors, fixes row 8, skips row 17, submits 38 to vetting while row 32 stays held back, then declines and pays the open invoice. Then the screenshots and the seven-pass review.
