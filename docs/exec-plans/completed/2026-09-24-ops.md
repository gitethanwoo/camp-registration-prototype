## Purpose / Big Picture

Camp operations staff (the Customer Experience Team persona Diane Carter, or the admin Alex Morgan) run the week of Overnight Camp (ON) Session 3, July 10–15, 2028. Before this plan they could see a small session overview and a registrations list, but nothing that answers the questions an operations lead asks in the last weeks before camp and on arrival day: who is not ready and why, which group and cabin is each camper in, whose cabinmate request is not met, and can this child be checked in right now.

After this plan a staff member can open four new pages under the "Operations" group of the admin sidebar, each working on real rows in the database:

- O1 Session readiness (`/admin/ops/readiness`): tiles for Registered 186 / 200, Waitlisted 9, Ready 159 and Needs attention 27; a roster with Payment, Waiver, CampDoc, Cabin and Activity columns; a needs-attention breakdown (19 CampDoc incomplete, 6 waivers missing, 8 balance due) that says the reasons overlap and by how much; a bulk "Send reminders" action that writes one HubSpot email per family to the outbox; and the capacity pools with Boys G6–8 full.
- O2 Group assignment board (`/admin/ops/groups`): pick a pool (Boys G6–8 has 50 campers), see five groups of 10 with a card per camper (grade, a "Request met" tag or a warning naming the separated friend), move a camper with a keyboard-accessible "Move to…" menu or by dragging, every move saved at once with an Undo toast, and an "Auto-suggest" that proposes moves which a person must approve.
- O3 Rooming board (`/admin/ops/rooming`): 16 cabins of 12 beds, 8 for boys and 8 for girls, with beds used, cabinmate requests met or not met, the unassigned campers, and a "Roster changed" flag listing the campers and requests that arrived after the last rooming review. The server refuses to put a camper in a cabin of the other gender or in a full cabin.
- O5 Check-in and check-out (`/admin/ops/check-in`): a tablet layout with a large search box, each camper's status (Ready, Blocked, Checked in, Checked out), blockers in words ("Balance due · Waiver missing"), a disabled check-in for blocked campers unless staff give an override reason (recorded in the audit log), and a check-out that requires choosing one of the household's authorized pickup adults and confirming their ID was checked.

## Context and Orientation

The repository is a WinShape camp registration prototype. `api/Camp.Api` is an ASP.NET Core minimal API on .NET 10 using EF Core against SQL Server. `web/` is a Vue 3 app using shadcn-vue components in `web/src/components/ui`. `e2e/` holds Playwright specs. `AGENTS.md` explains how slices plug in without editing shared files:

- An endpoint module is a class implementing `IEndpointModule` (`api/Camp.Api/Infrastructure/Modules.cs`); it is discovered by assembly scan, so a file in `api/Camp.Api/Features/Ops/` is enough.
- New tables are classes in the slice folder plus an `IEntityTypeConfiguration<T>`; `CampDbContext.OnModelCreating` applies every configuration in the assembly. Queries use `db.Set<T>()`.
- Demo data is an `ISeedModule` with `Order >= 100`, run after the core seed on every startup; it must check for its own rows first.
- `IAuditLog.Record(action, entityType, id, detail)` stages an append-only audit row; every staff mutation calls it before `SaveChanges`.
- `StaffUser` is the signed-in staff member (name and role), resolved from the cookie. Policies live in `api/Camp.Api/Auth/Identity.cs`.
- Web pages register through `web/src/features/ops/routes.ts` exporting `adminRoutes`; `meta.nav` adds a sidebar entry under a group ("Operations"). The admin scope switcher (`web/src/composables/useAdminScope.ts`) gives the current session id.

Terms used here: a capacity pool is a slice of a session's seats for a gender and grade band (Boys G6–8, capacity 50). A registration is one camper in one session (`Registrations` table), with `HealthStatus` (the CampDoc completion status for ON), `WaiverAcceptances` and money fields; its balance is price minus discount minus paid. CampDoc is the external health-form system used only by Overnight Camp; we show its completion status and a link, never health details. The outbox (`OutboxEvents`) is a table of messages a background worker delivers to HubSpot, which sends family email.

## Plan of Work

Milestone 1, the API. In `api/Camp.Api/Features/Ops/OpsEntities.cs` add `OpsCabin` (session, name, gender, beds, sort order), `OpsGroup` (session, pool, name, capacity, sort order), `OpsPlacement` (one per registration: cabin, group, suggested group, first activity choice, last reminder time, check-in time and actor, override reason, check-out time, actor and pickup adult), `OpsBuddyRequest` (a registration asks to be with another registration, with a created time), `OpsPickupAdult` (household, name, relationship, phone), and `OpsRoomingReview` (session, reviewed at, reviewed by), each with an `IEntityTypeConfiguration`. Add the `Ops` migration.

`OpsSeed` (Order 170) finds ON Session 3 and, if it has no cabins yet, creates 8 boys and 8 girls cabins of 12 beds, 5 groups of 10 per pool, placements for all 186 campers (86 boys and 86 girls assigned to cabins, 10 boys and 4 girls unassigned; Boys G6–8 fully grouped with one separated pair; a few unassigned in other pools), activity choices (a few not chosen), cabinmate requests (most met, one unmet in Girls Cabin 4), a rooming review timestamp just before the newest registration so one camper and one request show as "since the last review", pickup adults for every household, and a handful of campers already checked in.

`OpsReadModel.cs` holds the shared readiness computation: for a session, each confirmed registration's reasons (CampDoc or health incomplete, waivers signed below required, balance above zero). `OpsEndpoints.cs` maps under `/api/admin/ops`:

    GET  sessions/{id}/readiness           tiles, breakdown with overlap, pools, full roster
    POST sessions/{id}/reminders           { registrationIds } → one outbox email per family with open items
    GET  sessions/{id}/groups?poolId=      pools, groups, campers with request status and suggestions
    PUT  groups/placements/{registrationId}          { groupId | null } → autosave, returns previous group
    POST sessions/{id}/groups/suggest      { poolId } → stores suggested moves
    POST sessions/{id}/groups/suggestions/approve | dismiss   { poolId }
    GET  sessions/{id}/rooming             cabins, unassigned, requests, re-review items
    PUT  rooming/placements/{registrationId}         { cabinId | null } → gender and bed checks
    POST sessions/{id}/rooming/review      marks the roster reviewed
    GET  sessions/{id}/check-in            camper status, blockers, pickup adults
    POST check-in/{registrationId}         { overrideReason? } → 409 with blockers when blocked and no reason
    POST check-out/{registrationId}        { pickupAdultId, idChecked }

Integration tests in `api/Camp.Api.Tests/OpsTests.cs` cover the canonical numbers, the roster tie-out, authorization (anonymous 401, family and host 403, finance read-only), reminders to the outbox, moves with capacity and pool checks, auto-suggest approval, the gender and bed guards, the re-review flag, blocked check-in with and without override, and check-out with an adult from another household.

Milestone 2, the pages in `web/src/features/ops/`: `SessionReadiness.vue`, `GroupBoard.vue`, `RoomingBoard.vue`, `CheckIn.vue`, shared types in `types.ts`, and `routes.ts`. Each uses only `components/ui` primitives, and each works at 390px wide: the group board shows one group at a time on a phone with a group picker, the rooming board stacks cabins, and check-in opens the camper panel in a `Sheet`.
