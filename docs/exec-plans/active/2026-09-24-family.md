## Purpose / Big Picture

Before this change a signed-in family could register for Day Camp and see one checklist on "My family", but they could not add a child, change a child's details, see who else can use the account, look at a registration after the confirmation page, or pay what they still owe. A brand-new family (Sam Rivera) had an empty household and no way to fill it, so they could never register anyone.

After this change a family can do all of that from the family portal:

- F1, family home (`/family`): member cards for every adult and child, an "Add a family member" card, upcoming registrations, the payment plan with progress, and one combined checklist across all kids where every open item links to the screen that resolves it.
- F2, member profile (`/family/members/new`, `/family/members/:id`): add or edit a child or adult. A child's grade is derived from the date of birth with the Sept 1 rule and shown as "Grade 6 in fall 2028". Basic health (dietary, allergies, accessibility) lives on the member. Edits autosave.
- F3, household access (`/family/access`): adults with their access level, pending invitations, "Invite adult", "Cancel invitation", and "Revoke access" behind an `AlertDialog` that says guardian links stay.
- F4, my registrations (`/family/registrations`): every registration across ministries, grouped Upcoming, Past, and Cancelled, one card per order with status and balance, filterable by family member.
- F5, registration detail (`/family/registrations/:code`): participants, session, status, a checklist for this registration (with in-place waiver signing when one is missing), the payment summary, and "View payments and receipts".
- F6, payments and receipts (`/family/registrations/:code/payments`): each payment with date, amount, card last 4 and a receipt, the plan schedule with the next charge date, "Pay remaining balance" with the Fiserv sandbox card fields, and a failed-installment banner with Retry and the grace period.

To see it working: start the stack (see Concrete Steps), sign in as `sam.rivera@example.com`, add a child on My family, register that child for Day Camp with the deposit, and see the balance item on the checklist. Sign in as `maria.johnson@example.com`, register Avery and Mia on the payment plan, open My family, choose "Pay balance", pay $450 with card 4242 4242 4242 4242, and see the balance go to $0 with a receipt in the payment history.

## Context and Orientation

The repository is a WinShape camp registration prototype. The API is an ASP.NET Core minimal API in `api/Camp.Api` using EF Core against SQL Server. The web app is Vue 3 with shadcn-vue components in `web/`. Read `AGENTS.md` for the rules; this section repeats what this plan relies on.

A "slice" is a vertical feature owned by one folder on each side. This slice owns `api/Camp.Api/Features/Family/`, `web/src/features/family/`, `api/Camp.Api.Tests/FamilyTests.cs`, and `e2e/family.spec.ts`. It plugs into the app through seams that need no shared edits:

- `IEndpointModule` (in `api/Camp.Api/Infrastructure/Modules.cs`): any class implementing it is found by assembly scan and its `Map` method adds routes.
- `IEntityTypeConfiguration<T>`: EF picks up mapping classes from the assembly, so new tables are declared next to the slice code and reached with `db.Set<T>()`.
- `ISeedModule`: demo rows inserted on every startup after the core seed (`api/Camp.Api/Data/Seed.cs`); it must check for its own rows first. This slice uses `Order = 100`.
- `IAuditLog`: `audit.Record(action, entityType, id, detail)` stages an audit row before `SaveChanges`.
- `CurrentUser` (in `api/Camp.Api/Auth/Identity.cs`) is the signed-in guest: `HouseholdId`, `Name`, `Email`. Endpoints require `Policies.Family`. The household id always comes from the session cookie, never the request body or URL.
- Web routes: `web/src/features/family/routes.ts` exports `routes`, which `web/src/router.ts` adds under the guest layout. `meta.auth: 'family'` sends signed-out visitors through sign-in.

Domain facts used here. Money is stored in cents and formatted in the UI with `money()` from `web/src/lib/format.ts`. A `PaymentOrder` is one checkout: one card, one set of `Registration` rows (one per child), a list of `PaymentOperation` rows (charges, refunds), and for the payment plan a list of `Installment` rows. A registration's balance is `PriceCents − DiscountCents − PaidCents`. Grade uses a Sept 1 cutoff: `Eligibility.GradeFor(dob, sessionStart)`. The fake card processor is `FakeFiservGateway` (`api/Camp.Api/Integrations/PaymentGateway.cs`): the browser tokenizes a card through `/api/fiserv-sandbox/tokenize`, card 4242 4242 4242 4242 approves and 4000 0000 0000 0002 declines, and charges are idempotent per key.

Seeded personas (WorkOS emulator, `e2e/fixtures.ts`): Maria Johnson (returning family: David co-owner, Avery Grade 6, Mia Grade 4 in fall 2028) and Sam Rivera (new; the household is created empty at first sign-in).

## Plan of Work

Milestone 1, the API. Add `api/Camp.Api/Features/Family/FamilyEntities.cs` with two entities and their EF configurations: `HouseholdInvitation` (household, email, name, invited by, status Pending/Cancelled, created, expires after 14 days) and `BalancePayment` (order, idempotency key unique, amount, kind Balance or Installment, installment sequence, status Pending/Succeeded/Declined, card last 4, processor ref, decline reason, created). Generate the `Family` migration. Add `FamilySeed.cs` (`ISeedModule`, Order 100) for the past spring 2026 retreat. Add endpoint modules: `FamilyEndpoints.cs` for the home overview and members (F1, F2), `HouseholdAccessEndpoints.cs` for F3, `FamilyRegistrationEndpoints.cs` for F4 and F5 (including signing a missing waiver), and `FamilyPaymentEndpoints.cs` plus `BalancePaymentService.cs` for F6. Every endpoint is in a group that requires `Policies.Family` and filters by `CurrentUser.HouseholdId`; another household's order code returns 404.

The payment service works in three steps like checkout: in one transaction, compute the amount from the database (the whole balance, or the failed installment), and insert a `Pending` `BalancePayment`; charge the card with the payment's idempotency key; then in a second transaction record a `PaymentOperation`, spread the paid amount across the order's registrations by their remaining balance, mark the covered installments `Paid`, and set the payment's status. A repeated key returns the stored result. A second key while one is pending gets 409.

Milestone 2, tests. `api/Camp.Api.Tests/FamilyTests.cs` covers adding and editing members, household isolation, persona authorization (anonymous 401, staff 403), invitations and revoke, registrations grouping, balance payment (exact amount, idempotent double submit, declined card leaves the balance, nothing to pay), installment retry, and waiver signing.

## Idempotence and Recovery

The seed module checks for its program slug before inserting, so restarts are safe. The migration is additive (two new tables). To reset demo data, drop the `CampRegistration_Family` database and restart the API, which migrates and seeds again.
