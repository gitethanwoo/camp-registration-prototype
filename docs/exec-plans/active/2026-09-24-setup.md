## Purpose / Big Picture

Before registration opens, a WinShape administrator has to set up what families can buy: the program, its sessions and capacity pools, the price, deposit and payment plan, the cancellation and refund policy, discount rules and the waivers families sign. Today those values only exist in the seed, and the one setup page (`/admin/session`) can change a pool's capacity and nothing else. There is also no way to read the audit trail the rest of the app writes.

After this plan, Alex Morgan (the admin persona, `alex.morgan@winshape.example`) can sign in to the staff console and:

- K2: see every program by ministry with its type, forms, waivers and publish state; create a program as a Draft; submit it for approval; and see it go live on the guest site only after every step of the approval chain is approved by someone other than the submitter.
- K3: edit a session's name, dates, location, registration open and priority dates, and its capacity pools (add, rename, resize, remove an empty pool). Waitlist mode shows as locked to "Admin approval". Sessions at the retreat center show room capacity as read-only, "from Oracle Opera".
- K4: set price, deposit and the payment plan (installment count and final due date, with the computed schedule), and the cancellation and refund policy as a table of time windows. The staff cancel-and-refund screen (C3) reads that table. Changing a price never changes an existing order.
- K5: build discount rules (type, value, stacking, program or session scope, valid dates, usage cap) with a preview on a real registered camper, and a guard that refuses any rule that could take a camper's price below zero when stacked. Checkout and the guest quote honor the rule's scope, dates and cap.
- K7: see each waiver's versions with effective dates and acceptance counts per version, write a new draft version, submit it, and have a different admin approve it. Published versions are never edited in place; families who accepted an older version keep that record.
- K12: any staff member can read the audit log, filter it by event type, actor, dates and text, open an entry to see before and after values where they were recorded, and export the filtered list as CSV. Nothing can edit or delete an entry; the database refuses it.

To see it working: start the API and Vite (Concrete Steps), sign in as Alex, open "Programs" under Setup, open "Family Camp" (seeded Pending approval, step 1 already approved by Jamie Dalton), approve step 2, and see "Family Camp" appear at `/programs` on the guest site.

## Surprises & Discoveries

- Observation: dev sign-in gives every admin the same email (`admin@winshape.example`), so two admins in the API tests look like one person to the separation-of-duties checks.
  Evidence: `ApiFactory.SignInAsStaff` builds the email from the role. The tests therefore approve rows the seed says someone else submitted, and check that the author is refused.
- Observation: the core seed's "now" is 2027–2028 (waivers effective Nov 2027), but the app uses the real clock. Family Camp's past session is dated Summer 2026 so it is in the past on the real clock.
  Evidence: `Data/Seed.cs` waiver `EffectiveDate = new(2027, 11, 1)`; `SetupResults.Today` is `DateTime.UtcNow`.
- Observation: the sidebar lists every route's `meta.nav` entry for every staff role, so CET and Finance will see the Setup entries even though the setup endpoints require the Admin policy.
  Evidence: `web/src/layouts/AdminLayout.vue` builds `groups` from `router.getRoutes()` with no role check, and `RouteMeta` in `web/src/lib/nav.ts` has no role field.

## Decision Log

- Decision: Program publish state lives in a slice entity (`ProgramSetup`) with a two-step approval chain (`ProgramApprovalStep`: Camp director, then Ministry owner). The final approval publishes the program by setting the existing `CampProgram.IsPublished`, which is what the guest site already filters on. The submitter can't approve, and one person can't approve both steps.
  Rationale: K2's trap is "publish with no approval state". Tying publish to the last approval means there is no path to the guest site that skips approval. Separation of duties is the point of an approval chain; with only one admin persona, the seed provides a program whose first step another person already approved, so the demo still works.
  Date/Author: 2026-09-24 / Claude
- Decision: Programs are editable only while Draft. Pending approval and Published programs are read-only; "Return to draft" (which unpublishes a published program) makes them editable again.
  Rationale: approvers must approve what they read, and a live program changing under families is exactly what the approval chain exists to stop.
  Date/Author: 2026-09-24 / Claude
- Decision: Waiver versions are a slice entity (`WaiverVersion`). The existing `WaiverTemplate` row keeps holding the live version (its `Version`, `Body` and `EffectiveDate`), because checkout requires a signature for every `WaiverTemplate` of a program. Approving a new version archives the old version row and copies the new text onto the template. Past `WaiverAcceptance` rows keep their `Version` snapshot, and the old text stays in `WaiverVersion`.
  Rationale: adding a row per version to `WaiverTemplates` would make checkout demand a signature on every old version. This keeps checkout untouched.
  Date/Author: 2026-09-24 / Claude
- Decision: Discount rules are a slice entity (`DiscountRule`) one-to-one with the existing `DiscountCode`. A rule created in K5 by an admin creates an approved code. Codes requested by hosts and partners (staff-cx `DiscountRequest`) show in K5 read-only with a link to the C8 queue, and their requested terms are not enforced by this slice.
  Rationale: the C8 queue stays the only way a host code goes live, and its toast "It works at checkout now" stays true.
  Date/Author: 2026-09-24 / Claude
- Decision: `Features/Checkout.cs` and `Features/GuestEndpoints.cs` call `DiscountRuleGate` so a code with a rule only applies inside its scope and dates and under its cap; checkout claims a use with a conditional update in its seat transaction and releases it when the card is declined. `GuestEndpoints.cs` is outside this slice's allowed list; it gets a one-line call.
  Rationale: a rule that checkout ignores is a stub. The quote and checkout must agree, or a family sees a discount at review that checkout then refuses.
  Date/Author: 2026-09-24 / Claude
- Decision: The cancellation and refund policy is a per-session table (`RefundTier`: days before start, refund percent, basis, admin fee). The seed writes the rules the C3 quote hard-coded (60+ days: 100% of amounts beyond the deposit; 14–59: 50%; under 14: none) for every existing session, and `AdminEndpoints.CancellationQuote` reads the table through `RefundPolicy`. `AdminEndpoints.cs` is outside the allowed list; the change is limited to that quote.
  Rationale: K4's trap is "the policy as free text", and the plan requires refunds to read it. Seeding the old rules keeps C3's numbers unchanged for other slices.
  Date/Author: 2026-09-24 / Claude
- Decision: The payment plan template is the existing `Session.PlanInstallments` plus `Session.BalanceDueDate`; the schedule is computed by the existing `Pricing.PlanSchedule`. No change to `Pricing.cs`.
  Rationale: checkout already builds installments from these two values, so the K4 preview is exactly what a family gets.
  Date/Author: 2026-09-24 / Claude
- Decision: The audit log is made immutable in the database with an `INSTEAD OF UPDATE, DELETE` trigger on `AuditEvents`, added in the `Setup` migration. Before and after values are stored in a slice entity (`AuditChange`) linked to the audit row the slice's endpoints record.
  Rationale: "no edit or delete" should hold even for code that forgets. No existing code updates or deletes audit rows (checked with grep). The wave integrator must carry the trigger SQL into the combined migration.
  Date/Author: 2026-09-24 / Claude
- Decision: K3 is a new page, `web/src/features/setup/SessionSetup.vue` (`/admin/setup/sessions` for the session picked in the scope bar, `/admin/setup/sessions/:id` for any session), instead of growing `SessionEditor.vue`. `SessionEditor.vue` (`/admin/session`, open to all staff) keeps its capacity editor and gets one change: admins see a link to session setup, and other staff are told only an admin can change session details.
  Rationale: `/admin/session` is used by CET and Finance and by other slices' specs; putting admin-only editing there would mix two permission levels on one page. The new page reads the setup endpoints, which are Admin-only.
  Date/Author: 2026-09-25 / Claude
- Decision: Setup pages show an "Administrators only" message when the API answers 403, because the sidebar shows Setup entries to every staff role (see Surprises). The audit log is readable by all staff and needs no such message.
  Rationale: the nav has no role filter and adding one is a shared-layout change outside this slice.
  Date/Author: 2026-09-25 / Claude

## Context and Orientation

The repository is a WinShape camp registration prototype: an ASP.NET Core minimal API in `api/Camp.Api` (EF Core, SQL Server), Vue 3 with shadcn-vue components in `web/`, and Playwright specs in `e2e/`. `AGENTS.md` explains the "slice seams": an endpoint module is a class implementing `IEndpointModule` (found by assembly scan), entity mappings are `IEntityTypeConfiguration<T>` classes, demo data is an `ISeedModule` that runs after the core seed, staff mutations call `IAuditLog.Record` before `SaveChanges`, and web pages register through `web/src/features/<slice>/routes.ts` (the `adminRoutes` export, with `meta.nav` for a sidebar entry).

This slice owns `api/Camp.Api/Features/Setup/`, `web/src/features/setup/`, `api/Camp.Api.Tests/SetupTests.cs`, `e2e/setup.spec.ts`, and `web/src/pages/admin/SessionEditor.vue`. Money is stored in cents. A "capacity pool" is a slice of a session's seats (for example "Boys G6–8", 50 seats); `CapacityPool.Reserved` counts seats taken and only changes through a conditional SQL update so two people can't take the last seat. Policies (`api/Camp.Api/Auth/Identity.cs`): `Policies.Admin` is the admin role only; `Policies.Staff` is cet, finance or admin.

Shared files this plan edits, each recorded in the Decision Log: `api/Camp.Api/Features/Checkout.cs` and `api/Camp.Api/Features/GuestEndpoints.cs` (discount rules), `api/Camp.Api/Features/AdminEndpoints.cs` (refund table in the C3 quote), and `web/src/pages/admin/SessionEditor.vue` (a link to K3 for admins).

## Idempotence and Recovery

The seed module checks for its own rows before inserting, so restarting the API is safe. To start over, drop the slice database (`docker exec camp-registration-prototype-db-1 /opt/mssql-tools18/bin/sqlcmd -C -S localhost -U sa -P 'Camp_Dev_Passw0rd!' -Q "DROP DATABASE [CampRegistration_Setup]"`) and start the API, which migrates and seeds.
