## Purpose / Big Picture

Every WinShape program asks families a few questions at registration: T-shirt size, swimming ability, whether the family attends a church, whether a camper needs medication at camp. Today those questions are rows in the core `Questions` table, written once by the seed. Nobody can change them, there is no history of what a family was asked, and the three supported types (select, text, yes/no) can't express a date, a number, a long answer or a "pick several" question.

After this plan, an admin can build the registration form for a program in the staff console (screen K6, "Registration forms" under Setup). They pick question types (short text, long text, yes/no, single choice, multiple choice, date, number), say whether a question is asked once per household or once per camper, mark it required, and make it conditional ("show when *Does your camper need medication at camp?* is *Yes*"). A live phone preview shows the questions as a family will see them, including the conditional reveal. The live version is never edited: editing starts a draft (v3, say), the draft is sent for approval, and a different admin approves it before it replaces the live version. Old versions stay readable.

Families registering in the wizard (screen R3, `web/src/pages/guest/Register.vue`) answer the live version: household questions once, camper questions once per camper, follow-ups revealed only when their condition holds. The server enforces the same required and conditional rules at checkout, refuses answers of the wrong shape, and stores each answer with the form version and question it answered. Families see their answers on the registration detail page (F5), and staff see them on the admin registration detail (C3), labelled with the form version.

To see it working: start the API and Vite (Concrete Steps), sign in as Alex (admin), open Setup → Registration forms → "Day Camp · Rome", approve v2 that Jamie Dalton wrote, then start v3 and see that Alex can send it for approval but can't approve it himself. Then sign in as Maria, register Avery and Mia for Day Camp · Rome, answer "Yes" to the medication question for Avery and see the follow-up appear, and after paying find the answers on the registration page. Diane (CET) opens Avery's registration in the console and sees the same answers under "Form v2".

## Outcomes & Retrospective

Admins build a program's registration form in K6 (seven types, per camper or per family, required, conditional on an earlier yes/no or choice answer), watch it in a phone preview that uses the wizard's own field, and send a draft for a different admin's approval; version history keeps every version readable. The wizard asks the live version, checkout enforces the same required and conditional rules and stores each answer with its form version and question, and families (F5) and staff (C3) see the answers labelled "form vN".

Known gaps: campers placed on the waitlist at checkout have no registration, so their camper answers are not stored (household answers are), as before K6. Medication answers are shown to any staff role on C3; health-data gating belongs to the access slice. There is no drag-and-drop reordering (Move up and Move down instead) and no per-type validation rules beyond the type itself (length limits, date and number shape). On a phone, the question details sit below the list, so picking a question means scrolling to it.

## Context and Orientation

The repository is a WinShape camp registration prototype: an ASP.NET Core minimal API in `api/Camp.Api` (EF Core on SQL Server), a Vue 3 app in `web/` built from shadcn-vue primitives in `web/src/components/ui`, and Playwright specs in `e2e/`. `AGENTS.md` explains the seams a slice plugs into without editing shared files: an `IEndpointModule` class is discovered by assembly scan, an `IEntityTypeConfiguration<T>` is picked up by the DbContext, an `ISeedModule` runs after the core seed in `Order`, and `web/src/features/<slice>/routes.ts` adds pages (admin pages with `meta.nav` appear in the sidebar). Staff mutations call `IAuditLog.Record` before `SaveChanges`. Endpoints use the policies in `api/Camp.Api/Auth/Identity.cs` (`Policies.Admin` for setup, `Policies.Staff` for any console role, `Policies.Family` for a signed-in guest) and resolve `CurrentUser` or `StaffUser` instead of trusting ids in the request.

Terms used here. A "program" (`CampProgram`) is something families register for, such as Day Camp · Atlanta; it has "sessions" (dated weeks) with "capacity pools" (for example Grade 6, 20 seats). The "registration wizard" is `web/src/pages/guest/Register.vue`: participants, questions, health, waivers, review, payment. It loads everything from `GET /api/sessions/{id}/register-context` (`api/Camp.Api/Features/GuestEndpoints.cs`) and submits `POST /api/checkout`, handled by `CheckoutService` in `api/Camp.Api/Features/Checkout.cs`, which validates, claims seats, charges the fake Fiserv gateway, and writes `Registration` rows. A "household question" is asked once per registration order; a "participant question" is asked once per camper. A "conditional" question has a `ShowWhenKey` (another question's key) and `ShowWhenValue`; it is shown, and required, only when that question's answer equals (or, for multiple choice, includes) the value.

The setup slice's K7 waiver versions (`api/Camp.Api/Features/Setup/WaiverSetupEndpoints.cs`, `web/src/features/setup/WaiverTemplates.vue`) are the model for versions and approval here: Draft → Pending approval → Published → Retired, one open draft per owner at a time, the author can't approve, and approval is a conditional update so two approvers publish once. Its `SetupAudit.Record` helper stores before and after values for the audit log (K12).

## Plan of Work

Milestone 1, the API. In `api/Camp.Api/Features/Forms/FormEntities.cs` define `FormVersion` (program, version number, status, change note, who created, sent and approved it and when, published and retired times), `FormQuestion` (version, key, label, help text, type, scope, required, options, show-when key and value, sort order) and `FormAnswer` (order, registration or null for household answers, form version, question, value), with configurations: unique `(ProgramId, Version)`, at most one Draft or Pending approval version per program and at most one Published version per program (filtered unique indexes), unique `(FormVersionId, Key)` for questions. `FormRules.cs` holds the rules shared by the builder and checkout: structural validation of a version (keys, labels, options for choice types, conditions that point at an earlier question with a valid value, household questions never depending on camper questions) and answer validation (required and visible, value shape per type, hidden answers dropped). `FormsEndpoints.cs` maps the K6 API under `/api/admin/forms` (Admin) and the answers readers (`/api/admin/forms/registrations/{id}/answers` for Staff, `/api/family/forms/orders/{code}/answers` for Family). `FormsSeed.cs` (Order 150) creates v1 for Day Camp · Atlanta and Overnight Camp from their current questions plus the medication pair, and creates the Day Camp · Rome program, session, pools, waiver, a published v1 and Jamie Dalton's pending v2. The migration is `Forms`.

Milestone 2, checkout. `GuestEndpoints.cs` `register-context` returns the live version's questions (and a `form` object with id and version) when the program has one. `Checkout.cs` loads the live version and, when present, validates with `FormRules` instead of the legacy required check, rejects a request whose `formVersionId` is stale, and adds `FormAnswer` rows for each seated registration plus the household answers. Both are shared-file edits the master plan allows for this slice.

Milestone 3, the web. `web/src/features/forms/` gets `routes.ts` (admin route `setup/forms`, nav "Registration forms" under Setup), `FormBuilder.vue` (program list, question list, question editor, phone preview, versions), `QuestionField.vue` (one question rendered for a family, used by the wizard and the preview), `FormAnswers.vue` (answers card for F5 and C3), and `types.ts`. `Register.vue` renders questions through `QuestionField.vue` and sends `formVersionId`. `web/src/pages/admin/RegistrationDetail.vue` and `web/src/features/family/RegistrationDetail.vue` show `FormAnswers`.

Milestone 4, e2e and review. `e2e/forms.spec.ts` walks Alex, Maria and Diane. The family spec's Day Camp helper answers the new required medication question.

## Idempotence and Recovery

The seed module checks for its own rows (the Rome program slug, and a form version per program) before inserting, so restarting the API is safe. To start over, drop `CampRegistration_Forms` (see the master plan) and start the API, which migrates and seeds. The `Forms` migration is additive; at merge the integrator folds it into the wave's combined migration.

## Interfaces and Dependencies

New HTTP surface, all JSON:

    GET    /api/admin/forms                               Admin   programs with live and open versions
    GET    /api/admin/forms/programs/{programId}          Admin   versions with questions, approval state
    POST   /api/admin/forms/programs/{programId}/drafts   Admin   start a draft from the live version
    PUT    /api/admin/forms/versions/{id}                 Admin   save a draft (questions, change note)
    POST   /api/admin/forms/versions/{id}/submit          Admin   send for approval
    POST   /api/admin/forms/versions/{id}/approve         Admin   publish (not the author)
    POST   /api/admin/forms/versions/{id}/return          Admin   back to draft with a note
    DELETE /api/admin/forms/versions/{id}                 Admin   discard a draft
    GET    /api/admin/forms/registrations/{id}/answers    Staff   C3 answers
    GET    /api/family/forms/orders/{code}/answers        Family  F5 answers, own household only

`CheckoutRequest` gains an optional `FormVersionId`. `register-context` gains `form` (null or `{ id, version }`) and question types `ShortText`, `LongText`, `YesNo`, `SingleChoice`, `MultipleChoice`, `Date`, `Number` for programs with a live form.
