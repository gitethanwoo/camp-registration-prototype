## Purpose / Big Picture

WinShape Leadership (WSL) runs the Emerging Leaders Cohort, a program that a group leader registers on behalf of a team. Today the prototype shows the cohort on the Programs page but says "This flow isn't part of the prototype yet." After this work, a group leader (the seeded persona Pastor Dave, `pastor.dave@example.com`) can do three things end to end on real database rows.

First, on screen R8 ("group roster entry") the leader opens the cohort, chooses "Register your group", and types or pastes the attendees. Only a name is needed per row; an email is asked for but a row may be left partial. The leader pays for the whole group once with the simulated Fiserv card fields. Seats come out of the cohort's capacity pool atomically, so a group can never overbook the session.

Second, every attendee with an email gets a secure link (screen G1). The link opens a page that needs no account. It says who registered them, shows only their own information, and asks for a contact email, the program questions, and the versioned waivers. Submitting marks that attendee's forms Complete. The same page lets an attendee ask to withdraw.

Third, the leader's tracker (screen G2) shows how many attendees are Complete and Incomplete, lets the leader resend links (one or many), add a missing email, and approve or decline a withdrawal request. Approving refunds that attendee's price to the leader's card and releases the seat. The tracker states plainly that the leader can't complete forms on an attendee's behalf, and there is no edit-forms button.

To see it working: sign in as Pastor Dave, open "Emerging Leaders Cohort" from Programs, register a group, pay with 4242 4242 4242 4242, land on the tracker, press "Resend link" on an attendee, open the link shown in the dialog in a private window, submit the forms, and watch the tracker count move from Incomplete to Complete. The seeded group "Northside Fellowship leaders" shows the canonical numbers: 14 attendees, 9 Complete, 5 Incomplete, and one pending withdrawal request.

## Surprises & Discoveries

- Observation: a shadcn `AlertDialogAction` closes the dialog before its click handler runs, so a confirm handler that reads the dialog's target from state found it already cleared and did nothing.
  Evidence: the first e2e run showed the refund dialog close with no request sent. The tracker's confirm button is a plain `Button` inside `AlertDialogFooter`, which also keeps the dialog open with a spinner while the refund runs.

- Observation: the core seed already sets the cohort pool's `Reserved` to 14 (Carmen Ortiz's 14 attendees in the canonical dataset) without any rows behind it.
  Evidence: `api/Camp.Api/Data/Seed.cs`, `cohortS.Pools.Add(new CapacityPool { Name = "Attendees", ..., Capacity = 60, Reserved = 14 })`. The groups seed module adds exactly 14 attendee rows so the number is backed by data, and does not reserve seats again.
- Observation: the cohort program has no waivers or questions in the core seed, so an attendee link would have nothing to complete.
  Evidence: `Seed.cs` adds `Waivers` only to Overnight Camp and Day Camp. The groups seed module adds two waivers and four questions to the cohort program when they are missing.

- Decision: Group attendees are their own entity (`GroupAttendee`) rather than `Person` plus `Registration` rows.
  Rationale: a `Registration` requires a `Person` in a `Household`, and an attendee has neither; they may never create an account (FR-34). Inventing a household per attendee would pollute family search and the admin registration counts that other slices own. The cohort pool's `Reserved` still counts group seats, so capacity stays one number.
  Date/Author: 2026-09-24 / Claude
- Decision: The group is paid in full by the leader through a `PaymentOrder` with no `Registration` rows, charged by the slice-owned `GroupService` (`GroupService.CheckoutAsync`). `Checkout.cs` is untouched.
  Rationale: the cohort has no deposit or plan (Part 3 lists $450 per attendee). Reusing `PaymentOrder` and `PaymentOperation` keeps charges and refunds in the same ledger finance reads. Seats are claimed with one conditional UPDATE (`Reserved + n <= Capacity`) before charging; a decline releases them and returns the group to Draft with the roster intact.
  Date/Author: 2026-09-24 / Claude

## Context and Orientation

The repository is a .NET 10 minimal API (`api/Camp.Api`) over SQL Server with EF Core, and a Vue 3 single-page app (`web/`) built from shadcn-vue components in `web/src/components/ui`. Money is stored and sent in cents; the web formats it with `money()` from `web/src/lib/format.ts`.

Feature slices plug in without editing shared files. An API slice adds a class implementing `IEndpointModule` (see `api/Camp.Api/Infrastructure/Modules.cs`), discovered by assembly scan. New entities are mapped by an `IEntityTypeConfiguration<T>` in the slice folder, which `CampDbContext.OnModelCreating` picks up through `ApplyConfigurationsFromAssembly`. Demo rows come from an `ISeedModule` (runs after the core seed, ordered by `Order`, and must be idempotent). `IAuditLog.Record(...)` stages an audit row that the caller's `SaveChanges` commits.

Identity: guests sign in through WorkOS; on first sign-in a household is created by email. An endpoint that needs a signed-in guest uses `.RequireAuthorization(Policies.Family)` and injects `CurrentUser`, whose `HouseholdId` comes from the session cookie, never from the request. Anonymous endpoints (the secure link) use `.AllowAnonymous()` and identify the attendee only by the token.

Relevant existing rows: the Emerging Leaders Cohort (`Programs.Slug = 'emerging-leaders-cohort'`, `Type = Cohort`) has one session "September 2028" (Sept 13–15, 2028, $450) with one capacity pool "Attendees" (capacity 60). `IPaymentGateway` (`api/Camp.Api/Integrations/PaymentGateway.cs`) is the simulated Fiserv processor: `ChargeAsync(token, cents, idempotencyKey)`, `RefundAsync(processorRef, cents)`. The web obtains a token from `POST /api/fiserv-sandbox/tokenize`. `OutboxEvent` rows stand in for HubSpot email.

Web routes: a slice exports `routes` from `web/src/features/<slice>/routes.ts`; they become children of the guest layout. `meta.auth: 'family'` makes the router send a signed-out visitor through sign-in.

## Idempotence and Recovery

The seed module checks for its own rows before inserting, so restarting the API is safe. To start over, drop the slice database: `docker exec camp-registration-prototype-db-1 /opt/mssql-tools18/bin/sqlcmd -C -S localhost -U sa -P 'Camp_Dev_Passw0rd!' -Q "DROP DATABASE [CampRegistration_Groups]"`, then restart the API. Checkout is idempotent on the client's key: a repeated submit returns the first outcome instead of charging twice.

## Interfaces and Dependencies

HTTP surface (all JSON, money in cents):

    GET  /api/groups                                  family: my groups
    GET  /api/groups/start/{sessionId}                family: cohort session context for a new group
    POST /api/groups                                  family: create a Draft with a roster
    GET  /api/groups/{id}                             family (leader only): tracker data
    PUT  /api/groups/{id}/roster                      family (leader only, Draft only)
    POST /api/groups/{id}/checkout                    family: { idempotencyKey, cardToken }
    POST /api/groups/{id}/resend                      family: { attendeeIds } -> links sent
    PUT  /api/groups/{id}/attendees/{aid}/email       family: add or fix an email
    POST /api/groups/{id}/attendees/{aid}/withdrawal/approve|decline
    GET  /api/group-links/{token}                     anonymous: one attendee's forms
    POST /api/group-links/{token}/forms               anonymous: submit forms
    POST /api/group-links/{token}/withdrawal          anonymous: request withdrawal
